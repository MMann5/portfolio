# Story 1.2b: Internationalisation FR/EN — routing par locale, dictionnaire typé & sélecteur de langue

Status: done

<!-- Note: Validation is optional. Run validate-create-story for quality check before dev-story. -->

## Story

As a visitor,
I want to read the entire site in French or English via locale-prefixed URLs and a visible language switcher that remembers my choice,
so that I get the site in my language, consistently, and search engines see properly localized pages.

## Acceptance Criteria

1. **Routing par segment de locale + dictionnaire typé.** Étant donné le routing App Router par segments de locale (`app/[locale]/...`, locales `fr` et `en`) et un dictionnaire FR/EN typé, quand je visite `/fr` ou `/en`, alors la page est **générée statiquement par locale** (`generateStaticParams` retourne `[{locale:'fr'},{locale:'en'}]`, `dynamicParams = false`), le contenu affiché provient du dictionnaire pour la locale active, `<html lang>` reflète la locale (`fr`/`en`), des alternats `hreflang` (FR↔EN) et un `<link rel="canonical">` par locale sont émis, et **aucune chaîne visible n'est codée en dur hors du dictionnaire** (la page de démo héritée de la Story 1.2a est migrée pour lire ses textes depuis le dictionnaire). **Et** une clé de traduction manquante est détectable (échec de build / `tsc` — voir Dev Notes : le dictionnaire FR est typé `satisfies Dictionary`, toute clé absente casse `npm run typecheck` en CI).

2. **Redirection de `/` selon la préférence (proxy léger).** Étant donné le chemin racine `/` (et tout chemin sans préfixe de locale) et un visiteur de retour, quand la requête est traitée par le **proxy i18n léger** (`proxy.ts` à la racine du projet — `middleware.ts` est déprécié en Next 16, voir Dev Notes), alors il redirige (307) vers la locale stockée dans le cookie de langue (`NEXT_LOCALE`), ou — à défaut de cookie — vers la locale détectée depuis l'en-tête `Accept-Language` (fallback `en` si aucune correspondance) ; le proxy ne s'exécute pas sur `_next/*`, les assets statiques, `favicon.ico` ni les fichiers de métadonnées.

3. **Sélecteur de langue visible + persistance.** Étant donné le composant sélecteur de langue (`LanguageSwitcher` — autonome ici ; il sera monté dans la `Nav` en Story 1.3), quand je change de langue, alors la page s'affiche dans la langue choisie à l'URL préfixée correspondante (`/fr…` ↔ `/en…`, même chemin), le changement est annoncé aux technologies d'assistance, et ma préférence est persistée dans le cookie `NEXT_LOCALE` (max-age ~1 an, `Path=/`, `SameSite=Lax`) — conservée entre pages et entre visites.

> **Note de portée — ce que cette story livre :** la **machinerie i18n** (segments de locale, `generateStaticParams`/`dynamicParams`, proxy de redirection `/`, cookie de préférence, `<html lang>` dynamique, `hreflang`/canonical de base, dictionnaire typé + garde de complétude, composant `LanguageSwitcher`) + la **migration de la page de démo** sous `app/[locale]/`. **Hors scope :** le **modèle de contenu complet de toutes les sections** (`meta/hero/clients/about/experience/freelance/projects/stack/ai/contact/footer`) → c'est la Story 1.3 (qui *étend* le dictionnaire/contenu posé ici, pas le contraire) ; les **composants de shell** `Nav`/`GridSection`/`SectionHead`/`Footer` → Story 1.3 ; les **sections de page réelles** → Epic 2 ; le **SEO complet** (OpenGraph/Twitter, JSON-LD `Person`, `sitemap.xml`, `robots.txt`, finition `hreflang`/canonical multi-pages) → Story 4.3 ; les **traductions FR exhaustives de tout le contenu** → Story 2.4. Ici, le dictionnaire ne contient que les chaînes nécessaires à la page de démo + au sélecteur de langue, mais **en FR et EN**, avec la structure typée et la garde de complétude en place pour que 1.3/Epic 2 n'aient qu'à étendre. Ne pas sur-construire : pas de Nav, pas de sections, pas de `next-intl`/`next-international` (faire en vanilla App Router — cf. doc Next « Internationalization »).

### ⚠️ Pièges Next 16 (lire la doc — `AGENTS.md` : « This is NOT the Next.js you know »)

### Architecture i18n cible (résumé)

```
src/
  proxy.ts                       # (ou /proxy.ts racine) — redirige `/` et chemins sans locale → /<locale préférée>
  i18n/
    config.ts                    # locales = ['en','fr'] as const, Locale, defaultLocale='en', isLocale()
    dictionaries/
      index.ts                   # import 'server-only'; type Dictionary = typeof en; getDictionary(locale)
      en.ts                      # source de vérité du contenu (EN) — minimal (démo + switcher) pour cette story
      fr.ts                      # const fr = { … } satisfies Dictionary  ← garde de complétude
  components/
    LanguageSwitcher.tsx         # 'use client' — boutons/select EN|FR, cookie NEXT_LOCALE, router.push, aria-live
  app/
    globals.css                  # inchangé (tokens 1.2a) [+ éventuel .sr-only si absent]
    favicon.ico                  # inchangé
    [locale]/
      layout.tsx                 # ex-root layout : next/font sur <html lang={locale}>, generateStaticParams, dynamicParams=false, generateMetadata (dico + alternates + metadataBase)
      page.tsx                   # ex-page de démo, async Server Component, lit getDictionary(locale), monte <LanguageSwitcher>
      not-found.tsx              # (obligatoire) 404 minimal stylé « Technical Minimal », lien retour → /<locale>
```

- **Cookie** : nom `NEXT_LOCALE` (convention historique Next), `Path=/`, `Max-Age=31536000` (~1 an), `SameSite=Lax`, pas de `Secure` requis (mais inoffensif en prod HTTPS). Écrit côté client par le `LanguageSwitcher` (`document.cookie`). Le proxy le **lit** uniquement (pas besoin de l'écrire côté proxy — quand on visite `/` sans cookie, on détecte via `Accept-Language` et on redirige ; le cookie ne se posera qu'au premier choix explicite ; si tu veux *aussi* « mémoriser la langue de la 1re visite détectée », tu peux poser le cookie dans la réponse de redirection — optionnel, pas exigé par l'AC).
- **Détection `Accept-Language`** : implémentation maison suffisante pour 2 locales — splitter l'en-tête sur `,`, pour chaque entrée prendre la partie avant `;`, normaliser en minuscules, regarder le préfixe avant `-` (`fr-FR` → `fr`), retourner la **première** qui ∈ `{en, fr}` ; sinon `defaultLocale`. (Pas besoin de `negotiator`/`@formatjs/intl-localematcher` — n'ajoute pas ces deps pour 2 langues. Si un jour l'hébreu arrive — Epic 8 — on réévaluera.)
- **`hreflang`/canonical** : via `generateMetadata` → `return { metadataBase, alternates: { canonical: \`/\${locale}\`, languages: { en: '/en', fr: '/fr' } }, title, description }`. Next émet alors `<link rel="canonical" href="…/en">` et `<link rel="alternate" hreflang="en" href="…/en">` + `…hreflang="fr"…`. Un `hreflang="x-default"` peut être ajouté (`languages: { 'x-default': '/en', en: '/en', fr: '/fr' }`) — recommandé, peu coûteux. La finition SEO (sitemap, robots, OG, JSON-LD, vérif crawl) = **Story 4.3** — ne pas la faire ici.
- **`<html dir>`** : FR et EN sont LTR → pas de `dir` à gérer (rester implicite `ltr`). Le RTL (hébreu) est Epic 8 — hors scope ; mais en posant `lang={locale}` dynamiquement on prépare le terrain.

### Garde de complétude des traductions (FR19 / AC#1)

Mécanisme retenu : **type-driven**. `en.ts` est la **source de vérité** (forme + contenu de référence). Dans `dictionaries/index.ts` : `export type Dictionary = typeof en;`. Dans `fr.ts` : `const fr = { …toutes les clés… } satisfies Dictionary; export default fr;`. Conséquence : une clé manquante, en trop, ou mal typée dans `fr` ⇒ erreur `tsc` ⇒ `npm run typecheck` échoue ⇒ **CI rouge** (la CI lance déjà `typecheck`). C'est le « build failure / lint warning » exigé par l'AC, sans outillage custom. (Alternative possible : un test runtime au build qui compare les clés — inutile ici, le type fait le job ; ne pas sur-ingénier.) **Important pour 1.3 / Epic 2** : quand le vrai modèle de contenu (toutes les sections) sera ajouté, garder ce pattern (`en` = source, `fr satisfies Dictionary`) pour conserver la garantie. Documenter ce contrat dans un commentaire en tête de `dictionaries/index.ts`.
